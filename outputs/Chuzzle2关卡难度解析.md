# Chuzzle 2 v2.75：关卡与难度控制解析

分析对象：用户提供的 Chuzzle+2_2.75_APKPure.xapk。本文分析的是这个版本，不将初代、经典附加模式和主线地图混为一谈。

## 结论

原作使用“地图位置分配难度等级 → 各玩法把等级翻译成参数 → 补球筛选控制随机收益与可动性”的分层结构。难度同时作用于匹配密度、行动空间、压力增长、目标负担和特殊规则，远不只是提高分数目标。

对我们已有 H5 原型最有价值的两项，是补球后的连锁抑制和锁带来的操作空间收缩。当前 H5 的等概率补球、4–6 种花色、步数用尽立即失败，是原型自行采用的简化规则，不等于原作参数。

## 证据与边界

- REA 已完成 XAPK、基础 APK、ARM64 split 的识别与安全解包。
- 核心逻辑位于 lib/arm64-v8a/libChuzzle2_ndk.so。该库保留了大量 C++ 函数符号。
- 当前 REA 的 Windows Ghidra 适配器不接受 ARM64 ELF；Hopper 不支持本机，IDA 未配置。因此反编译使用本机已安装的 Ghidra 12.1.4 独立完成。这些反编译结果不冒充 REA Evidence。

## 1. 主线关卡：先生成地图，再给地图节点分配难度

已确认：Overworld::GenerateWorld 选择地图尺寸与难度上下界，再交给 MakeGrid。这里的地图尺寸是世界地图节点网格，不能误读成单局消除棋盘大小。

Overworld::MakeGrid 在符合条件的节点上读取 StepsToStart，并做近似以下的计算：

```
t = clamp(距起点的路径步数 / 参考路径长度, 0, 1)
节点难度 = trunc(难度下界 + (难度上界 - 难度下界) * t)
```

参考长度在代码中由一处 StepsToStart 结果减 3 得到，不宜在未验证终点语义前简化成“全地图最远距离”。

邻近带特定位标记的地图格时，节点难度还会加 1，上限 14。该标记的完整玩法语义未继续还原，因此不直接称作 Boss 邻格。

GenerateWorld 的一般分支中，难度上界会封顶于 14，前两张世界使用单独分支；另有模式标志影响地图尺寸与区间。不能简单概括为每关固定增加一级。

含义：世界负责安排从容易到困难的节奏，各个玩法负责决定具体难在哪里。

证据：chuzzle2-核心函数.txt，Overworld::GenerateWorld @ 0051fcbc；MakeGrid @ 005218d8，尤其 StepsToStart 及 param_3/param_4 插值段。

## 2. 同一难度等级，在不同玩法里变成不同参数

已确认：Game::GoFillTheBottle、GoTactical、GoSpeedChuzzle、GoUnlockChuzzle、GoStinky 等函数分别创建并配置 Board，多个模式仍使用 6×6 消除棋盘。

### 十步策略玩法的一个明确例子

GoTactical 将两个步数相关字段设为 10，同时随难度改变目标和颜色候选数量。

| 内部难度索引 | 颜色候选数 | 装瓶目标，内部单位 |
|---:|---:|---:|
| 0 | 7 | 35 |
| 1 | 7 | 40 |
| 2 | 8 | 40 |
| 5 | 8 | 50 |
| 10 | 9 | 62 |
| 14 | 9 | 75 |

这里的装瓶目标不是界面上显示的总分，不能直接换成 H5 的 900 分。高难度分支还会修改其他特殊元素字段，未给未恢复字段强行命名。

颜色数并非仅凭字段猜测：Chuzzle::Randomize 会将 Board+0x804 的值传给随机函数，生成颜色/类型索引；代码还包含特定索引排除和特定模式重选。因此“候选数”比宣称所有情况下完全等概率且种类数固定更准确。

重要区别：Board::JustFinishedMoveEX 对步数耗尽有不同分支。某些配置进入额外落锁惩罚，另一些才进入失败状态，不能把全部十步玩法理解成第十一步绝对禁止。

### 速度玩法

GoSpeedChuzzle 不仅提高装瓶目标，还缩短压力增长的时间尺度。在已恢复的高难度分支中，其时间尺度近似：

```
k = 原始难度超过 3 后放缓增长所得的内部等级
T = max(2.0, 4.75 - 0.5 * (k - 7))
压力增量 = 1 / (T * 全局更新频率相关值)
```

这里的 T 可解释为压力增长时间尺度，但未运行验证其与玩家秒表时间完全一致，故不直接宣称每 T 秒必定落锁。低难度跳转表未完整恢复，公式不外推到所有等级。

含义：限步玩法提高每步要求；速度玩法提高单位时间要求。不同玩法不能共用一条只调目标的曲线。

证据：chuzzle2-玩法参数函数.txt，GoTactical @ 003bbcf0；GoSpeedChuzzle @ 003bcc08；Chuzzle::Randomize @ 0041fe20。chuzzle2-核心函数.txt，JustFinishedMoveEX @ 0044b7e8。

## 3. 补球不是单纯掷骰子：原作会干预自动收益

已确认：FillHolesEX 中，Board+0x81c 开关启用时，调用 SortChuzzles 和 MinimizeCascades。多个普通玩法初始化都会将这个开关设为 1。

MinimizeCascades 的主体读取 GetMatches，对匹配中属于传入候选列表的毛球调用 Chuzzle::Randomize，并排除类型索引 14。存在有界重试结构。因此它会修改指定候选球，不是只统计连锁次数。

可以确认：有专门的连锁抑制处理。不能确认：它保证所有补球都没有连锁，或根据实时胜率决定给玩家坏球。

这是我们之前 H5 一步暴涨上万分时最应该补上的机制：原作并没有完全放任随机补球产生无限的免费收益。颜色数也不同，不能把全部差异都归因于这个函数。

## 4. 同时存在可动性检查，但不是任何时候都保送有解

已确认：FillHolesEX 的特定条件分支会调用 GetHint；若未找到有效移动，会对候选列表重随机化，再尝试连锁抑制和提示检查。重试次数有上限，常见值 100，另有特定类型配置为 1000。

CheckGuaranteeMovesStinky 也包含 GetHint、Randomize 和 MinimizeCascades，说明特殊玩法有额外的可动性处理。

边界：这些处理由开关、玩法和状态条件控制，而且有重试上限。不能据此声称原作永远不会死局，更不能声称每关一定能通。

设计意义：随机性分两层管理——避免太多自动收益，同时避免在需要保障的场景中立即无路可走。这两件事应分别控制。

证据：chuzzle2-核心函数.txt，FillHolesEX @ 0043cfdc；MinimizeCascades @ 004432e4；CheckGuaranteeMovesStinky @ 00443b20。

## 5. 锁的本质是减少可操作空间

已确认：RehupLimitDrag 检查拖动列表中的锁字段，存在锁时将允许拖动范围从很大值收紧为 0.2。锁直接影响移动，并非仅提高目标。

PossiblyLockChuzzle 的落锁检查包含：

1. 该配置是否启用随机落锁。
2. 当前是否处于允许触发的状态，以及相关冷却字段是否允许。
3. 当前锁数量是否达到上限。
4. 装瓶进度较低时缩减触发阈值；代码读取当前装瓶量字段，而非简单读取关卡百分比。
5. 进行随机阈值比较，然后调用 LockRandomChuzzle；更高进度的附加分支可能改变传入参数。

函数后半有未恢复跳转表，因此不声称已经还原全部锁类型和后期频率。

解释：同样的锁数，如果分布在更多不同的行列，会影响更多移动路线。因此实际设计时，应测可移动行列和有效匹配动作数，而不只数锁。此句是设计推论，不是声称原版直接使用该指标评分。

|---:|---:|---:|---:|

ChanceToLock 不应直接读成“每一步有相同数值的百分比必定落锁”：运行代码有状态门控、进度修正、上限和随机比较边界。表里缺少某些等级时的回退策略，本次没有完整还原。

能看出的设计意图：前两级不放锁；后面同时增加目标和锁容量；第三级到第四级，锁上限增加而原始触发值反而降低，说明不是所有压力维度都必须单调上升。

## 7. 挑战规则改变策略，不只是增加数字

原生库包含以下玩家可见规则文本，已经确认文本存在，未逐条运行验证所有回调组合：

- 每次移动结束落一把锁。
- 打破一把锁，随后落下两把锁。
- 每两回合锁住两只毛球。
- 只有四只以上匹配才能得分。
- 只有组合消除才能得分。
- 组合消除或连锁触发落锁。
- 五只以上成组匹配奖励一步。
- 连锁不提供额外计分奖励。

这些规则属于每日挑战等系统，不能直接认定每条都用于普通主线。它们展示了组合难度的手段：让“追大连锁”“拆锁”“求每步收益”等目标产生冲突。

## 8. 有难度修正机制，但不足以宣称按失败次数动态放水

Overworld::FixDifficulty 会按关卡类型读取一份进度数组；若节点原始难度高于该值，则将节点难度设为该值 + 1，并设置一次性处理标记，同时增加玩家资料中的 DifficultyMod 对应项。

WinCurrentLevel 还会复制该资料数组，并对其他符合条件的地图节点作扣减修正。这说明难度除了世界位置，还与按类型保存的进度状态有关。

由于本次未完成该数组所有写入点和完整调用时序的审计，不能把它说成“连续失败后降难”“根据玩家胜率实时操纵补球”或精确还原的 DDA 算法。它更适合暂称为按类型进度修正/限制。

证据：chuzzle2-核心函数.txt，FixDifficulty @ 0054033c；chuzzle2-玩法参数函数.txt，WinCurrentLevel @ 0053d708。

## 给当前 H5 的实施建议

以下是基于已发现机制的设计建议，并非原版配置复刻，本次没有修改游戏。

1. 优先实现补球控制：补球后检测自动匹配，只重抽本轮新生成的猫；设置重试上限，并允许可配置的连锁机会。不要通过偷偷取消已成立的玩家匹配来控制难度。
2. 增加锁：分别配置初始锁、触发时机、生成间隔、同时存在上限。先用可移动行列数和有效动作数评估空间压力。
3. 将关卡拆为“玩法模板 + 难度索引 + 随机种子”。每种玩法单独映射颜色/花色候选数、目标、压力、步数与特殊猫参数。
4. 先制作普通装瓶、十步策略、速度压力三类，再安排由易到难的关卡节奏。当前小猫仅六种，如扩大候选种类，必须同时添加清晰的新花纹/标识。
5. 用多种操作策略跑种子样本，记录目标完成所需步数、有效动作数、自动连锁贡献、死局率和锁覆盖范围。用中位数和极端连锁分布校准目标，避免只提高目标来掩盖失衡。

最值得先复刻的核心，是“控制补球带来的收益，控制锁留下的操作空间，再用目标与预算要求玩家更高效率”。
